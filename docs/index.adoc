= Quarkus RSQL

This extension lets REST endpoints accept https://github.com/jirutka/rsql-parser[RSQL] filters, such as `name==Apple;weight=gt=100`, and turns them into Hibernate ORM queries.
It works with Hibernate ORM with Panache and with plain HQL/JPQL.

== Installation

The extension requires Java 17 or later and Quarkus 3.27 or later, and has been tested on Java 17, 21 and 25 with Quarkus 3.27, 3.33 and 3.40.

Add the `io.github.matheuslealpa:quarkus-rsql` dependency to your build file.

With Maven, add the following to your `pom.xml`:

[source,xml]
----
<dependency>
    <groupId>io.github.matheuslealpa</groupId>
    <artifactId>quarkus-rsql</artifactId>
    <version>1.0.2</version>
</dependency>
----

With Gradle, add the following to your `build.gradle`:

[source,gradle]
----
implementation("io.github.matheuslealpa:quarkus-rsql:1.0.2")
----

== Usage

Translate the filter with `Rsql.toQuery` and pass the result to Panache:

[source,java]
----
@GET
public List<Fruit> list(@QueryParam("filter") String filter) {
    RsqlQuery query = Rsql.toQuery(filter, Fruit.class);
    return Fruit.find(query.query(), query.parameters()).list();
}
----

A `null` or blank filter matches all entities.

The generated query selects the entity with the alias `r` (also available as `Rsql.ALIAS`), for example `select r from Fruit r where r.name = :p0`.
Use the alias to qualify properties in other clauses, such as sorting:

[source,java]
----
Fruit.find(query.query(), Sort.by(Rsql.ALIAS + ".name"), query.parameters()).list();
----

=== Filter parameters

Receive the filter as an `RsqlFilter` to convert it directly from a request parameter:

[source,java]
----
@GET
public List<Fruit> list(@QueryParam("filter") @DefaultValue("") RsqlFilter filter) {
    RsqlQuery query = filter.toQuery(Fruit.class);
    return Fruit.find(query.query(), query.parameters()).list();
}
----

The filter is only parsed by `toQuery`, once the entity is known, so an invalid filter throws an `RsqlException` instead of failing the parameter conversion, which REST reports as `404 Not Found` for query parameters.
Use `@DefaultValue("")` to match all entities when the parameter is missing, as JAX-RS passes `null` otherwise.

=== Sorting

RSQL only describes filters, so the sort is a separate parameter: a comma-separated list of selectors, each prefixed with `-` to sort in descending order, such as `-price,farm.name`.
Pass it with the filter to get a query that ends with an `order by` clause:

[source,java]
----
@GET
public List<Fruit> list(@QueryParam("filter") @DefaultValue("") RsqlFilter filter,
        @QueryParam("sort") @DefaultValue("id") RsqlSort sort) {
    RsqlQuery query = filter.toQuery(Fruit.class, sort);
    return Fruit.find(query.query(), query.parameters()).list();
}
----

Or with strings, `Rsql.toQuery(filter, sort, Fruit.class)`.

Sort selectors follow the same rules as the filter: they must be persistent attributes, `@RsqlIgnore` and the accepted selectors apply, and associations in their paths are joined, once even if the filter uses them too.
Only basic properties can be sorted, not associations or embeddables themselves.
As the query is already sorted, don't pass a `Sort` to Panache too.

=== Nested paths

Selectors can navigate through single-valued associations (`@ManyToOne`, `@OneToOne`) and embeddables (`@Embedded`), for example `farm.name==Sunny` or `farm.address.city==Lisboa`.

Associations are joined with left joins, so entities whose association is `null` are still matched by the other conditions of an `or`: `farm.name==Sunny,name==Lime` also returns fruits without a farm named `Lime`.
An association used more than once in a filter is joined only once, except inside collections, where each comparison joins its own (see below).

=== Collections

Selectors can also go through collections (`@OneToMany`, `@ManyToMany`, `@ElementCollection`), and compare the elements of a collection of basic values directly: `fruits.name==Apple` matches the farms with some fruit named Apple, and `tags==fresh` the fruits with some tag `fresh`.

Each comparison is translated to a correlated subquery (`exists`), so the entity is never duplicated and the result can be paged and sorted as usual.
This gives the following semantics:

* `tags==fresh;tags==promo` matches the entities that have some tag `fresh` and some tag `promo`, not necessarily the same element.
* `tags!=promo` and `tags=out=(a,b)` match the entities with no such element, not those with some other element.
* `tags=null=` and `tags=notnull=` match the entities whose collection is empty or not.
* Collections can be nested, such as `fruits.tags==fresh`, and combined with associations, such as `fruits.farm.name==Sunny`, which are joined inside the subquery of each comparison.

A collection of entities or embeddables can't be compared itself, compare a property of its elements instead: `fruits.id==1` rather than `fruits==1`.
Selectors through a collection can't be sorted. Map collections aren't supported.

=== Operators

[cols="1,1,2"]
|===
|RSQL |HQL |Example

|`==` |`=`, or `like` if a `String` value contains `+*+` |`name==Apple`, `name==*apple*`
|`!=` |`<>`, or `not like` |`color!=RED`
|`=gt=` or `>` |`>` |`weight=gt=100`
|`=ge=` or `>=` |`>=` |`harvested>=2026-10-01`
|`=lt=` or `<` |`<` |`weight<100`
|`=le=` or `\<=` |`\<=` |`weight=le=100`
|`=in=` |`in` |`color=in=(RED,GREEN)`
|`=out=` |`not in` |`color=out=(RED)`
|`=null=` |`is null` |`harvested=null=`
|`=notnull=` |`is not null` |`harvested=notnull=`
|===

Use `;` (or `and`) and `,` (or `or`) to combine conditions, and parentheses to group them.

=== Values

Values are converted to the type of the entity field: `String`, numbers, `BigDecimal`, `BigInteger`, `Boolean`, enums, `UUID`, `LocalDate`, `LocalDateTime`, `LocalTime`, `OffsetDateTime` and `Instant`.

In a `String` comparison, `+*+` matches any sequence of characters. Other characters, including `%` and `_`, are matched literally.

=== Security

Selectors are resolved against the Hibernate ORM metamodel, so they must be persistent attributes of the entity: transient fields can't be filtered.
Values are always bound as named parameters, so a filter can't inject HQL.

Any persistent attribute can be filtered by default, including through associations.
Comparisons such as `passwordHash=gt=m` let a client guess a value one character at a time from the results, so don't expose sensitive attributes.
Annotate them with `@RsqlIgnore` to exclude them from every filter:

[source,java]
----
@Entity
public class Owner extends PanacheEntity {

    public String name;

    @RsqlIgnore
    public String passwordHash;

}
----

To expose only some properties to the clients of an API, pass the accepted selectors to `Rsql.toQuery`, which then apply to the filter and to the sort:

[source,java]
----
RsqlQuery query = Rsql.toQuery(filter, Fruit.class, Set.of("name", "color", "farm.name"));
----

Ignored attributes and selectors that aren't accepted are rejected as unknown properties, so that their existence isn't revealed.

An invalid filter, an unknown property or a value of the wrong type throws an `RsqlException`, which you can map to a `400 Bad Request` response.

=== Current limitations

* Map collections (`Map<K, V>` attributes) can't be used in a path.
* Native mode hasn't been tested yet.
